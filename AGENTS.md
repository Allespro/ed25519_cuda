# AGENTS.md

CUDA port of the [orlp/ed25519](https://github.com/orlp/ed25519) library (SUPERCOP "ref10" arithmetic), extended with Tor v3 onion address generation. `.cu` implementations and `.cuh` headers live flat in the repo root.

## Commands

```bash
make test             # build with g++ on the CPU (no GPU, no nvcc needed) and run the unit tests
make test-sanitize    # same, under AddressSanitizer + UndefinedBehaviorSanitizer
make test-gpu         # build with nvcc and run the same tests on a GPU
make clean
python3 tests/gen_vectors.py > tests/test_vectors.h   # regenerate test vectors
./test_colab.sh [sm_XX]   # one-shot GPU build + run, default arch sm_75
```

`make test` prints `N checks, M failures` and exits nonzero on any failure.

## What is and is not verified

- `make test` (CPU, 870 checks) is the only verification that has actually been run. It compiles the real `.cu` files with a small CUDA emulation layer (`tests/cpu_sim/`) that runs kernels sequentially, one thread at a time, on host memory.
- The nvcc build and execution on a real GPU have **not** been run. Nothing in this repository confirms that `make test-gpu` or `test_colab.sh` compiles or works. CUDA-specific syntax (`<<<>>>`, real `threadIdx`/`blockDim`, memory layout, `__constant__` placement) is unverified. Run `make test-gpu` on a CUDA machine before relying on any of it.
- The CPU emulation cannot detect race conditions, out-of-bounds device memory access, or performance problems.

## Testing

`test.cu` contains `main()` and all unit tests (it takes no command line flags). Expected values come from `tests/test_vectors.h`, generated by `tests/gen_vectors.py` from an independent big-integer Python implementation of RFC 8032 / RFC 7748 plus `hashlib`. The generator self-checks against the published RFC 8032 and RFC 7748 vectors before emitting anything.

To add a test: add a table to `gen_vectors.py`, regenerate, and add a `run_*_tests()` function in `test.cu`. Use `launch(kernel, grid, block, args...)` from `tests/launch.h` to invoke kernels on either target, and `check_hex` / `check_int` from `tests/common.h` to compare.

The vector tables are `static` and live in a header included by one translation unit (`test.cu`); do not include `tests/common.h` from another `.cu`.

## Architecture

Bottom-up; each layer only calls layers below it.

1. `fixedint.cuh` pulls in `<stdint.h>`.
2. `fe.cu` field arithmetic mod 2^255-19. `fe` is `int32_t[10]` in radix 2^25/2^26 limbs.
3. `sc.cu` scalar arithmetic mod the group order (`sc_reduce`, `sc_muladd`).
4. `ge.cu` Edwards curve group operations; `precomp_data.cuh` holds the `__constant__` tables used by `ge_scalarmult_base`. Never hand-edit the tables.
5. Hashing: `sha512.cu` (streaming SHA-512), `keccakf.cu` (Keccak-f[1600] permutation only), `sha3.cu` (SHA3-256 sponge built on `keccakf`).
6. Ed25519 operations, one file each: `keypair.cu`, `sign.cu`, `verify.cu`, `add_scalar.cu`, `key_exchange.cu`; `seed.cu` reads `/dev/urandom` on the host (Linux/Unix only, asserts otherwise).
7. `onion.cu` builds Tor v3 addresses from public keys: `checksum = SHA3-256(".onion checksum" || pk || 0x03)[0..2]`, `address = base32(pk || checksum || 0x03)` (56 chars).

## Kernel and batch API conventions

- Every batch kernel starts with `int compute_index = blockIdx.x * blockDim.x + threadIdx.x; if (compute_index >= limit) return;` and then calls a per-element `__device__` function. `limit`, not the grid size, decides how many elements are processed; extra threads are idle.
- Buffers are tightly packed per element: public keys/seeds/shared secrets 32 bytes, private keys 64, signatures 64, onion addresses `ONION_ADDRESS_LEN + 1` (including the terminating `\0`).
- `message_len` in the sign/verify kernels is a cumulative offsets array of `limit + 1` entries: message `i` is `message[message_len[i] .. message_len[i+1])`. Passing per-message lengths reads out of bounds.
- `*_single_keypair` kernels use one key pair for all messages. `*_multi_keypair` kernels take `key_mapping[i]` (or `NULL` meaning identity) to pick the key pair for message `i`.
- `ed25519_kernel_add_scalar_batch` applies one scalar to every key pair. `ed25519_kernel_add_multi_scalar_batch` uses `scalar[scalar_mapping[i]]`.
- `onion_search` writes `found[i] = 1` when address `i` starts with `prefix` and ends with `suffix` (either may be `NULL`). It only flags matches in a preallocated array; it does not collect them.

## Gotchas

- `fe_frombytes` ignores the top bit of its input. It is `(s mod 2^255) mod p`, not `s mod p`. Public keys and coordinates are always 255-bit, so this is correct for its intended use, but do not use it to reduce arbitrary 32-byte values.
- `ed25519_kernel_key_exchange` clamps the scalar with `k[31] &= 63; |= 64` (the Ed25519 secret-scalar clamp), which differs from RFC 7748's `k[31] &= 127` for arbitrary input. Results match X25519 whenever the private key is a real Ed25519 secret scalar, which the RFC 7748 vectors in the tests cover.
- `ed25519_kernel_add_scalar` ignores the top bit of the scalar (`scalar[31] & 127`).
- `fe.cu` and `ge.cu` left-shift negative values in carry chains. This is undefined behaviour by the C++ standard; g++, ASan/UBSan builds and the tests all produce correct results, and it is inherited from ref10. UBSan reports it on every run (many lines of `left shift of negative value`), which is noise, not a test failure.
- `__device__` functions are defined in one `.cu` and called from another, so nvcc needs `-rdc=true`.
- `readme.md` is the original C library's readme. It documents `ed25519.h`, a `src/` folder, DLL builds and `ED25519_NO_SEED`, none of which exist here. The batch-kernel API is declared in `ed25519.cuh`.
